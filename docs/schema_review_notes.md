## 1. condition 放 Card 主檔 ── 確認合理，保留

- **查證結果**：放 Card 是 PRD 明文需求（PRD 618 行「品相/鑑定分數混在一起→價格失真→Card 要記錄 condition/grade」）。
- seed 已有 PSA10 卡，前後端（grade 篩選、顯示、後台輸入）均已支援。
- `raw` 是卡牌圈標準術語（裸卡/未鑑定），命名沒問題。
- **現行模型**：一筆 Card = 一個「設計 + 品況」組合（噴火龍 raw 與 噴火龍 PSA10 是兩筆）。這是**刻意**用最簡方式支援鑑定卡。
- **已知取捨**（非 bug）：同設計不同品況會有 name/cardNumber/setName/imageUrl 重複，cardNumber 不唯一。資料量小，MVP 可接受。
- **未來（資料量大時）**：可考慮加「卡片變體 variant」層消除重複，但非 MVP 範圍。
- **結論**：無需修改。

## 2. 多來源時 latestPrice 取值 ── 需團隊決定 ⚠️

- **問題**：一張 Card 可有多個 PriceSource（seed 的皮卡丘 V 就有 2 個）。
  抓價迴圈（priceSync.service.js:49）逐一處理來源，每個來源都覆寫 `card.latestPrice`，
  最終值 = 「迴圈裡最後處理的那個來源」的價格。
- 來源順序來自 `findMany` 無 orderBy → 等同 DB 預設順序，偏隨機。
- **影響**：同張卡多來源價不同時，主檔「最新價」會飄（每次可能不一樣）。
- **PRD 相關**：PRD 617 行「必要時不要硬算平均」→ 排除「取平均」這個解法。
- **選項**：
  - A. 每張卡指定一個 primary source，主檔只反映它
  - B. 取最低價（比價網常見：顯示最便宜何處買）
  - C. 維持現狀（MVP seed 多數卡單一來源，暫不痛）

### Ken 個人偏好（待全組討論）
- **傾向取最低價（B）**，不採 primary source。理由：若綁定單一主要來源，就失去爬多來源的意義，
  產品會退化成「某交易網的價格鏡像」，稱不上真正的價格追蹤器。
- **但「最低價」前必須先去雜訊**，否則最低價往往最髒：
  - 過濾異常值（極端價會打擊使用者對追蹤器的信心）
  - 全方位情境捕捉：運費、短期促銷、是否真的有庫存
  - 全部過濾後再取最低，才有參考價值（難度因此上升，看大家想法）
- **「最低價」定義**：每個來源各自最新一筆價，取其中最小者。

### 補充：難度分層與隱藏依賴（review 提醒）
- 去雜訊難度不一，不該綁一起做：
  - 過濾異常值 🟢 可行（現有 `isSuspiciousPrice` >50% 波動已有雛形，可延伸）
  - 運費 / 促銷 🟡 偏難（來源頁多無結構化欄位，需各站客製）
  - 庫存狀態 🔴 很難（各站結構不同、最易壞，多半超出 MVP）
  - 建議：MVP 先做「過濾異常值」，運費/庫存列未來進階。
- **隱藏依賴**：跨來源取最低價需先統一幣別（不能 JPY 直接比 USD），
  因此本項依賴項目 4 的幣別換算 → 若要做比價，priceTwd 換算就從「可選」變「前置條件」。

## 3. 冗餘摘要欄位（latestPrice / latestCurrency / lastFetchedAt） ── 確認合理

- **用途**：列表頁顯示多張卡的最新價時，免去每張卡都去 PriceSnapshot 撈最新一筆（反正規化優化）。
- **同步機制**：寫快照與更新主檔包在同一 `$transaction`（priceSync.service.js:95-126），
  不會發生「快照寫了、主檔沒更新」的不一致。✅
- 前端列表頁/詳情頁確實讀用這些欄位。
- **結論**：冗餘是值得的，保留。（注意：取值問題見第 2 項）

## 4. 貨幣顯示 / priceTwd 死欄位 ── 需團隊決定 ⚠️

- **現況**：前端 `fmtPrice`（CardListPage.jsx:8）直接顯示「幣別代碼 + 數字」如 `JPY 1,200`，
  **無任何換算**。台灣使用者看到的是日幣，不是台幣。
- **priceTwd 死欄位**：schema / migration / PRD 都有，但**無任何程式寫入、前端也沒讀**，永遠是 null。
- **與第 2 項疊加**：latestCurrency 同樣「最後來源說了算」，多來源不同幣別時，
  顯示的**幣別本身也會飄**（JPY ↔ USD），比數字飄更糟。
- **PRD 相關**：PRD 357 行 priceTwd 標「可選」→ MVP 顯示原幣別不算違規。
- **選項**：
  - A. 實作台幣換算（串匯率 API，抓價時填 priceTwd，前端顯示台幣）
  - B. 拿掉死欄位 priceTwd（不做換算就別留空欄位）
  - C. MVP 原樣顯示，但 UI 標清楚來源與幣別
- **建議**：MVP 走 C；priceTwd「要嘛補實作（A）、要嘛移除（B）」二選一，
  不要留著一個永遠空白的欄位造成誤解。

### Ken 個人偏好（待全組討論）
- **先做 C**（MVP 原樣顯示原幣別 + UI 標清楚來源與幣別）。
- 同時跟組員討論兩件事：
  1. 死欄位 priceTwd 是否移除。
  2. 串接匯率 API 的「必要性 + 難易度」，再決定要不要執行方案 A。
- **討論時須帶出依賴**：因為項目 2 想做「跨來源取最低價」，幣別換算的必要性被往上推，
  匯率換算可能不再是純可選，而是比價功能的前置條件。

## 5. isSuspiciousPrice 異常價格偵測 ── 漏洞清單（PRD 列為加分功能）

- **現行邏輯**（normalizePrice.js:45-49）：只判斷「新價 vs 前次價」浮動是否 > 50%，
  比較對象是 `source.card.latestPrice`（priceSync.service.js:93）。
- **PRD 定位**：異常價格偵測是**加分功能**（PRD 603 行），非 MVP Must。
- **漏洞（依嚴重度排序）**：
  1. 第一次抓價無基準（prevPrice 為 null → 回 false）：首筆荒謬價（¥1 或天價）永遠不被標記。
  2. 比較對象 latestPrice 是「最後來源說了算」（連動項目 2/4）：可能拿新日幣價比舊美金價 → 比較無意義。
  3. 完全不看幣別：¥1000 vs $10 會被當暴跌。
  4. 標記了卻照樣顯示（line 110 無條件寫入 latestPrice）：可疑價仍變成前台最新價 → 標記等於沒保護。
  5. 抓不到緩慢漂移：每次漲 40% 不觸發，複利後已爆走。
  6. 只比單一前值：若前一筆本身是雜訊，比較就失準（理想：比近期中位數）。
  7. 對稱 50% 門檻過粗：真實市場暴漲也會被誤標。
- **改善優先序（CP 值）**：#1（首筆加絕對合理範圍）、#4（可疑價不直接當 latestPrice 或前台標警示）、
  #6（改用近期中位數當基準）。
- **註**：#2、#3 在採「單一幣別 MVP」策略後會自動消失（比較對象同幣別）。

## 附註：FK 外鍵（已決定保留，記錄結論）

- 會議曾傾向「不用 FK」，但經查：去除 FK **不簡化實作**（seed 巢狀 create、service 的 include
  用的是 Prisma 關聯，非 DB 約束；去除只是 datasource 加 `relationMode = "prisma"` 一行）。
- 單一 PostgreSQL（Supabase）、資料量小，FK 是 Prisma 自動建的「免費髒資料防護網」。
- **結論**：保留現狀（與 Kai「確定不需要再修」一致）。低風險，不糾結。
